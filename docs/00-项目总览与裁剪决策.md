# 00 · 项目总览与裁剪决策

> 项目代号：`campus-run` ｜ 中文名：校园跑腿平台 · AI 调度客服中台
> 定位：**简历项目**（非上线运营）｜ 范围：**单校区** ｜ 技术栈：Java 17 + Spring Boot 3.5 + Redis 7 + Python Agent + Vue3
> 文档版本：**v1.2（2026-11-17）**，本版依据 `13-文档评审与修订建议.md` 修订，与 v1.1 的差异见各文档末尾"变更记录"。

## 1. 项目一句话

校园内的代取快递、代买餐、代打印、代还书跑腿平台。Java 侧负责订单、资金、状态机与确定性派单；Redis 负责抢单并发闸门、GEO 检索、消息流与缓存；Python Agent 负责自然语言下单、订单进度问答、超时派单决策、售后工单初判；Vue3 提供学生端、骑手端、运营端三套界面。

**简历上的定位说法**：一个"Java 主业务 + Redis 高并发 + LLM Agent 增强"的三层分工项目，验证了 Agent 在企业场景下的正确接入方式 —— 不接管关键链路、只接管非确定性决策、全量工具调用可审计。

## 3. 范围裁剪决策（这个项目的价值一半在"不做什么"）

### 3.1 明确做

| 模块 | 内容 | 简历价值 |
|---|---|---|
| 订单主流程 | 下单 → 派单 → 抢单 → 取件 → 送达 → 确认/自动确认 → 结算 | 业务闭环 |
| Redis 十二项 | 缓存三件套、GEO、Lua、Stream、ZSet 延迟队列、BitMap、HLL、限流、Redisson 锁、幂等、热 key 治理 | 高并发亮点 |
| Agent 四件 | 自然语言下单、订单进度/FAQ 问答、超时派单决策、售后工单初判 | 差异化亮点 |
| 三端前端 | 学生端、骑手端、运营端（Vue3 + Element Plus） | 可演示 |
| 压测数据 | 抢单 200 并发、缓存前后 QPS 对比、缓存击穿 | 能量化 |

### 3.2 明确不做（砍掉，写进文档避免后期纠结）

| 砍掉项 | 原因 | 替代方案 |
|---|---|---|
| 多校区 / 跨校区调度 | 简历项目无收益，复杂度翻倍 | `campus` 表保留，只放 1 条数据，预留扩展 |
| 真实微信支付 | 需商户资质 | 本地模拟支付网关，签名回调模拟 |
| 真实短信/推送 | 需运营商通道 | 平台内消息表 + WebSocket 推送，短信打日志 |
| 骑手实时轨迹 | 地图 SDK 计费、轨迹算法耗时 | 取件/送达两点定位打卡 |
| 微信小程序 | 需主体认证、审核周期 | H5（Vue3），答辩手机浏览器即可演示 |
| 复杂派单算法（实时路径规划） | 投入产出比低 | 距离 + 信用分 + 空闲度的加权打分 |
| 分布式部署 / 集群 | 简历项目单机足够 | Docker Compose 单机多容器；`05` §11 写清"上集群要改什么" |
| 完整财务对账系统 | 无真实资金流 | 结算单 + 抽佣 + 退款/赔付流水（新增 `refund_record`） |
| 实名认证对接公安库 | 不可行 | 骑手资质人工审核（运营端通过/驳回） |
| Agent 自主支付/退款 | 资金安全边界 | Agent 只能建草稿、建工单、建议加价；支付与退款永远走人工/前端 |

### 3.3 降级与兜底（简历上要能讲"我考虑了失败"）

1. **Agent 不可用** → Java 侧全套降级：表单下单、规则派单，功能不中断（`agent.enabled=false` 开关）。
2. **模型超时/幻觉** → 8s 超时、Pydantic 强校验、条款白名单比对、金额规则复算、置信度低于阈值转人工。
3. **Redis 挂** → 订单查询回落 MySQL，抢单降级为 DB 乐观锁（性能差但可用），派单退化为 DB 轮询。
4. **支付回调丢失** → `PayTimeoutTask` 扫超时未支付订单主动关单；模拟支付支持手动重放回调。
5. **抢单落库异常** → v1.2 改为**同步落库**，失败立即回滚 grab key 与骑手在手单计数，用户看到明确失败原因（不再有"先成功后回滚"的窗口）。

## 4. 关键业务参数（全文唯一口径，代码里必须一致）

### 4.1 计价规则（金额单位：分，全链路整数）

| 项 | 规则 |
|---|---|
| 起步价 | 300 分（≤1000m 且 ≤2kg） |
| 距离加价 | 超出 1000m，每满 500m +50 分（向上取整） |
| 重量加价 | 超出 2kg，每满 1kg +100 分（向上取整） |
| 加急费 | +200 分（期望 30 分钟内送达），入 `urgent_fee` |
| 夜间费 | +100 分（21:00–06:00 下单），入 `night_fee`；营业时段 07:00–23:00，故实际只在 **21:00–23:00** 产生 |
| 单笔封顶 | 2000 分（只封顶 `fee+distance+weight+urgent+night`，不含后续加价；触发封顶时 `fee = 2000 - urgent_fee - night_fee`，订单标注 `capped=true`） |
| 平台抽佣 | 实付的 10%，最低 30 分（基数 = `total_fee`，含加价） |
| 首轮之外加价 | 系统/Agent 加价入 `raise_fee`，单次 ≤300、累计 ≤500 |

**费用字段口径（v1.2 新增，必须按这个落库）**：

```
fee        = base + distance + weight      # 基础服务费
urgent_fee = 加急费（0 或 200）
night_fee  = 夜间费（0 或 100）
raise_fee  = 系统/Agent 加价累计（0 ~ 500）
urgency_fee= urgent_fee + night_fee + raise_fee   # 冗余列，供展示
total_fee  = fee + urgency_fee
```

### 4.2 派单与抢单

| 项 | 值 |
|---|---|
| 首轮圈选半径 | 1500m |
| 首轮等待 | 90s |
| 第二轮 | 半径扩至 3000m + 加价 100 分，再等 90s |
| 第三轮 | 调 DispatchAgent 决策；超阈值或累计加价达上限 → `ESCALATE_CS` + 建工单 + `dispatch_paused=1` |
| 终止条件 | `dispatch_paused=1` 后从 `cr:zset:timeout` 移除，等待人工；不再自动重派 |
| 骑手同时在手单 | 最多 3 单 |
| 抢单频率阈值 | 单骑手 10 分钟内抢单 > 20 次 → 限流并记 `grab_record` 异常（cost_ms 也参与脚本识别） |
| 抢单落库 | **同步** UPDATE（`WHERE status='WAITING' AND rider_id IS NULL`），Stream 只做通知与失败记录异步落库 |

### 4.3 信用分与结算

| 项 | 值 |
|---|---|
| 骑手初始信用分 | 100 |
| 准时送达 | +2（单日上限 +10，`cr:credit:daily` 计数） |
| 超时（>30min） | −5 |
| 投诉成立（`liable_party=rider`） | −10 |
| 低于 60 分 | 抢单直接拒绝（40906），需运营调整/解封 |
| 结算时点 | 订单 `COMPLETED` 后立即生成结算单（T+0），`settlement.order_id` 唯一 |
| 结算后赔付 | 生成 `refund_record`（`bear_party=rider` 时关联 `settlement_id` 做负向调整） |

### 4.4 Agent 决策阈值

| 项 | 值 |
|---|---|
| 单次加价上限 | 300 分 |
| 单笔累计加价上限 | 500 分（只统计 `raise_fee`） |
| 建议赔付 > 1000 分 | 强制主管审核（`role=2`） |
| 决策置信度 < 0.6 | 升级人工 |
| 意图置信度 < 0.7 | 澄清话术，连续 2 次失败转人工 |
| 槽位补全最多轮次 | 3 轮，超轮转表单 |
| 工具调用上限 | 下单 5 / 派单 3 / 工单 4 次 |
| Agent 单日 token 预算 | 50 万 token（`cr:budget:{yyyymmdd}`），超预算只走 FAQ 与规则话术 + 转人工 |
| Agent 可见工具数 | 14 个（见 `03` §6，`refund_order`/`update_order_status` 永不注册） |

## 8. 架构四条铁律（写在这里，任何实现冲突时以此为准）

1. **单一写入口**：MySQL 只被 Java 写；Python 不持有业务库连接，所有读写走 `/internal/agent/**`。
2. **确定性归 Java，非确定性归 Agent**：抢单、状态流转、结算、圈选骑手是代码；加价、改派、定责、话术是模型。Agent 挂在关键链路之外。
3. **权限分级 + 全量审计**：Agent token 只能读 + 建草稿/建工单/建议加价；退款、超额加价、强制取消仅运营 token。每次工具调用写 `agent_tool_log`，每次模型调用写 `agent_turn_log`。
4. **口径唯一**：金额拆分、状态迁移、退款记账、错误码各只有一处权威定义（`02` §3/§5、`03` §9、`08` §5）。任何文档改动必须同步 SQL 与测试，否则视为未完成。
