> 目标：简历项目也要有可量化的质量结论。**三组数字必须在简历上出现**：抢单并发正确性、缓存前后 QPS 对比、Agent 条款引用准确率。

## 3. 并发与压测

### 3.1 场景 A：抢单并发正确性

| 项 | 配置 |
|---|---|
| 数据 | `tests/sql/seed-pressure-test.sql`：200 骑手（在线、信用 100、GEO 已写）+ 1 张 WAITING 订单 |
| 线程数 | 200 |
| 目标 | 同一订单 `POST /api/rider/task/{no}/grab` |
| 断言 | MySQL 中 `rider_id` 只有 1 个；接口成功数 = 1；`grab_record` 仅 1 条 SUCCESS；无 `FAIL_STATUS` |
| 对比 | 关闭 Lua 改 DB 乐观锁，记录失败率与 P99（写进报告） |
| 指标 | 成功率、平均 RT、P99 RT、失败原因分布 |

### 3.2 场景 B：订单详情缓存前后对比

| 项 | 配置 |
|---|---|
| 线程数 | 50，Ramp-up 5s，循环 50 次（2500 请求） |
| 目标 | `GET /api/user/order/{no}`（同一订单） |
| 对照 | 缓存关 / 缓存开（先预热） |
| 指标 | QPS、平均 RT、P99、DB 慢查询 |
| 预期 | QPS ≥ 3 倍；P99 从 ~30ms 降到 ~5ms |

### 3.3 场景 C：缓存击穿

| 项 | 配置 |
|---|---|
| 线程数 | 300，同时请求同一订单 |
| 操作 | 把缓存 JSON 的 `expire_at` 改到过去（**不要 DEL**，否则没有旧值可返回，与"读不阻塞"设计不符） |
| 验证 | 只有 1 个线程拿到重建锁；DB 查询次数 = 1；其余返回旧值 |
| 记录 | DB QPS 峰值、重建耗时 |

### 3.4 场景 D：Stream 消费滞后（可选）
持续建单 100 单/分钟，观察 `XLEN` 与 `XPENDING`；`XAUTOCLAIM` 是否把超时 pending 收回。

## 4. 一致性校验用例（定时任务验证）

| 校验 | 方法 | 频率 |
|---|---|---|
| Redis 状态镜像 vs MySQL | 抽样 TOP 50 活跃订单比对 `status/rider_id` | 每分钟 |
| `grab` key 存在但订单无骑手 | 扫 `cr:order:grab:*`（限量），订单仍 `WAITING` → 删 key + 告警 | 每 5 分钟 |
| 结算单缺失 | `COMPLETED` 且无 `settlement` → 补生成 | 每小时 |
| 支付超时未关闭 | `DRAFT` 且 `created_at < now-15min` → 关闭 | 每分钟 |
| 自动确认 | `DELIVERED` 且 `delivered_at < now-30min` 且无未完结工单 → 完成 | 每分钟 |
| 工单卡 `PENDING` | 超 10 分钟未转 `REVIEWING` → 标 `agent_failed` | 每 10 分钟 |
| 在手单数漂移 | `rider.active_order_count` vs 实际 `ACCEPTED/PICKED/DELIVERED` 单数 | 每 10 分钟 |
| 布隆重建 | Redis 重启后扫描近 30 天订单回填 | 启动时 |

## 5. Agent 评测执行方式

见 `06` §10。执行细节：

| 项 | 做法 |
|---|---|
| 样本 | `agent-python/eval/datasets/*.jsonl`（60 条） |
| 运行 | `python -m eval.run --set order --model <model>` |
| 输出 | `eval/results/{date}-{set}.csv`：样本、期望、实际、是否通过、延迟、`trace_id`、`prompt_version` |
| 复现 | 每条结果必须能按 `trace_id` 查到 `agent_turn_log`（模型 + Prompt 版本） |
| 抽检 | 每类 5 条人工看自然度（1–5 分） |
| 报告 | `docs/评测报告.md`：指标表 + 5 个失败案例 + 归因分布 |

**失败案例必须写归因**（Prompt / 检索 / 样本标注 / 工具问题），这是面试官最想看的部分。

## 6. 缺陷记录规范

| 级别 | 定义 | 处理 |
|---|---|---|
| P0 | 主流程中断（下单/支付/抢单不可用） | 当天修 |
| P1 | 关键分支错误（越权、金额错、状态错、超卖） | 2 天内修 |
| P2 | 体验问题（提示不清、样式错） | 阶段末统一修 |
| P3 | 优化项 | 记录不修 |

记录：`docs/bug-list.md`（编号、现象、复现、根因、修复 commit）。**"根因"一列最能体现成长**。
