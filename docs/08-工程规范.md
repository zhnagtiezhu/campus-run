**四条硬规则**：
1. `domain` 包不 `import` Spring、Mapper、Redis —— 保证纯 JUnit 可测。
2. 状态变更只能走 `OrderStateMachine.requireTransit(...)`；`UPDATE task_order SET status` 只允许出现在 `OrderService` 的 3 个方法（settle / cancel / exception）。
3. Controller 里不允许 `if (status.equals(...))` 之类的业务判断。
4. **Redis / Stream / HTTP 调用不能出现在 `@Transactional` 方法内部**（必须放到事务提交后，见 §3）。

## 3. 事务与锁边界（v1.2 新增，写代码前必看）

### 3.1 哪些方法开事务

| 方法 | 事务 | 事务内做什么 | 事务后做什么 |
|---|---|---|---|
| `OrderService.createOrder` | ✅ | 校验草稿/报价 + insert task_order + 写状态流水 | 删空值缓存、写 `cr:order:status` |
| `PayService.handleCallback` | ✅ | `pay_record` 条件更新 + 状态机 DRAFT→WAITING | ZADD 延迟队列、XADD Stream、WS |
| `GrabService.grab` | ❌（单条 UPDATE 自带原子性） | Lua 占位 → 单条条件 UPDATE | 回滚或 XADD/WS |
| `OrderService.cancel` | ✅ | 状态 CAS + 写退款记录（PENDING） | 锁 `cr:lock:refund` 执行 mock 退款 → 更新 refund 状态 |
| `SettlementService.settle` | ✅ | insert settlement（唯一索引）+ 状态 COMPLETED | 清缓存、WS、信用分 |
| `TicketService.resolve` | ✅ | 状态 CAS REVIEWING→RESOLVED + insert refund_record + ticket_event | 锁内执行退款、发消息 |
| `DispatchService.applyDecision` | ✅ | 状态迁移/加价 + insert dispatch_decision | ZADD、WS、建工单 |
| `TicketService.create` | ✅ | insert ticket + ticket_event | XADD `cr:stream:ticket` |

**实现工具**：`TransactionSynchronizationManager.registerSynchronization(afterCommit(...))` 或 `@TransactionalEventListener(phase = AFTER_COMMIT)`。**不要**在事务里发 HTTP / 写 Redis / 发 Stream。

### 3.2 锁的层

| 场景 | 手段 | 说明 |
|---|---|---|
| 抢单 | Redis Lua（唯一赢家）+ DB 条件 UPDATE | 不用分布式锁 |
| 加价 | DB 条件更新 `raise_fee+? <= 500` + `cr:lock:raise` | 锁只做体验优化，DB 是最终裁判 |
| 结算 | `cr:lock:settle` + `settlement.order_id` 唯一 | 双保险 |
| 退款/赔付 | `cr:lock:refund` + `refund_record.idem_key` 唯一 + 状态 CAS | 三重 |
| 工单处理 | `UPDATE ticket SET status=... WHERE status='REVIEWING'` | CAS 即可 |
| 缓存重建 | `SET NX cr:order:lock` | 短锁，不阻塞读 |

### 3.3 事务传播与异常

- 只对 `RuntimeException`/`Error` 回滚；受检异常必须显式 `rollbackFor = Exception.class`。
- 内部工具接口的 service 方法不要吞异常，让 `GlobalExceptionHandler` 统一转 `Result`。
- 异步线程（缓存重建、批量落库）不继承事务，必须显式传参。

## 4. AOP 与登录上下文（对标苍穹外卖）

| 能力 | 做法 |
|---|---|
| 公共字段自动填充 | MyBatis-Plus `MetaObjectHandler`：insert 填 `created_at/updated_at/delete_flag`，update 填 `updated_at`；实体字段加 `@TableField(fill = ...)` |
| 登录上下文 | `LoginContext`（ThreadLocal）：`userId`、`role`、`traceId`；拦截器解析 JWT 后 set，`finally` remove |
| 审计 | `AgentToolInterceptor` 在 `finally` 写 `agent_tool_log`（主路径）；`ToolAuditAspect` 可选做方法级补充 |
| 幂等 | `IdemInterceptor` 或 `@Idem` 注解 + AOP（写接口）；内部工具同样生效 |
| 分页 | MyBatis-Plus `PaginationInnerInterceptor`，`page_size` 上限 50；不混用 PageHelper |
| 导出 | EasyExcel（A-21），流式写出，避免大内存 |

> 这几项是"苍穹外卖技术栈"的标志性写法，面试官会默认你会；文档里必须能指出来。

## 5. 命名规范

| 场景 | 规范 | 示例 |
|---|---|---|
| 数据库表/字段 | 小写下划线 | `task_order`, `order_no` |
| Java 类 | 大驼峰 | `OrderStateMachine` |
| Java 方法/变量 | 小驼峰 | `grabOrder` |
| **HTTP/JSON 字段** | **小写下划线** | `order_no`, `fee_delta`（Jackson 全局 `SNAKE_CASE`） |

## 6. 日志规范

| 级别 | 用途 | 必须包含 |
|---|---|---|
| INFO | 建单、支付、抢单成功/失败、状态变更、结算、工单处理、退款 | `trace_id`, `order_no` |
| WARN | 抢单回滚、缓存重建失败、Agent 降级、限流触发 | 同上 + 原因 |
| ERROR | 数据不一致、Stream 死信、退款失败、Agent 连续失败 | 同上 + 堆栈 |
| DEBUG | 仅开发：SQL、Lua 参数、完整 prompt | 不入生产 |

统一格式：`[trace_id] [order_no] action=GRAB_FAIL reason=FAIL_GONE rider=1001 cost_ms=1`

**禁止**：打印手机号、身份证、完整 prompt 中的隐私；必要时脱敏。

**traceId 流向**：前端生成（32 hex）→ Java `TraceIdFilter` 入 MDC + LoginContext → 内部工具 Header 透传 → Python 中间件读取 → Python 调 Java 回传 → 日志与 `agent_tool_log.trace_id` 一致。

## 7. 异常与错误码实现约定

| 层 | 做法 |
|---|---|
| `domain` | 抛 `BizException(ErrorCode.XXX)`，不返回 boolean |
| `service` | 捕获底层异常转 `BizException`，非业务异常包装 `SYSTEM_ERROR` |
| `controller` | 不写 try-catch，由 `GlobalExceptionHandler` 统一处理 |
| 全局处理器 | `{code, message, data:null, trace_id}`；`BizException` 用其 code，其他一律 50001 + ERROR 堆栈 |
| 参数校验 | Jakarta Validation，失败 40001 并返回字段名 |
| 内部工具 | 异常也必须返回结构化 code（40302/409xx），禁止裸 500 |

**错误码不得硬编码数字**，全部来自 `ErrorCode`，与 `03` §9 一一对应（31 个）。

## 11. 编码自检清单（每次提交前 30 秒）

- [ ] 新增字段是否同步更新 `02` 与 `03`？
- [ ] 状态变更是否走状态机？有没有直接 UPDATE status？
- [ ] 写了 Redis key 是否设 TTL？key 是否符合 `cr:` 规范？是否在 `05` key 表里？
- [ ] 新增写接口是否支持 `Idempotency-Key`？key 是否按"用户动作"生成？
- [ ] 涉及金额是否用 `int` 分？费用是否按六字段拆分？
- [ ] 事务里有没有 Redis/HTTP/Stream 调用？
- [ ] 日志是否带 `trace_id` 与 `order_no`？有无隐私？
- [ ] Agent 新工具是否在 registry 标了权限？是否写审计？
- [ ] 失败路径是否给用户可执行的下一步？
- [ ] 是否加了降级分支（Redis 挂 / Agent 挂）？

## 13. 代码评审关注点（自查用）

| 维度 | 看什么 |
|---|---|
| 正确性 | 状态迁移合法；金额只算一次；幂等覆盖 |
| 并发 | 抢单/加价/结算/退款是否有锁或唯一约束；缓存重建是否可能锁泄漏 |
| 一致性 | 缓存删除顺序；Stream 消费幂等；失败是否回滚 |
| 事务 | 事务边界是否合理；事务内是否调外部系统 |
| 可观测 | 关键路径日志；错误是否有 traceId |
| 安全 | 越权校验（学生查别人订单、Agent 传别人 user_id）；内部接口只内网；SQL 参数化 |
| 降级 | Redis/Agent 挂掉时的行为是否明确 |
