## 3. 关键时序

### 3.1 表单下单 → 支付 → 进入派单

```
学生前端         Java                         Redis              MySQL
   │  POST /quote │                             │                  │
   │─────────────►│ 校验范围/时段/申报价值 → PriceCalculator → quote_token
   │◄─ fee_detail │                             │                  │
   │  POST /order │                             │                  │
   │─────────────►│ 校验 quote_token → 落 DRAFT ─────────────────────►│
   │◄─ order_no   │                             │                  │
   │  POST /pay   │                             │                  │
   │─────────────►│ 模拟网关 → 回调（SYSTEM）→ pay_record=1 ──────────►│
   │              │ 状态 DRAFT→WAITING（状态机）  │                  │
   │              │ 写延迟队列 ZADD cr:zset:timeout(+90s) ────────────►│
   │              │ XADD cr:stream:dispatch ORDER_PAID ─►│           │
   │◄─ 支付成功    │                             │                  │
```

### 3.2 抢单（Redis 闸门 + **同步**落库，v1.2 关键变更）

```
骑手前端            Java                    Redis                   MySQL
   │ POST grab    │                          │                       │
   │─────────────►│ RateLimiter ────────────►│                       │
   │              │ EVAL grab Lua ───────────►│ 成功→SET grab key     │
   │              │◄─ 1/0/2/3/4/5 ────────────│ HINCRBY busy_count    │
   │              │ 同步 UPDATE ... WHERE status='WAITING' AND rider_id IS NULL │
   │              │──────────────────────────────────────────────────►│
   │              │ 影响行数=0 → DEL grab key + HINCRBY -1 + 回滚原因    │
   │              │ XADD stream:dispatch GRABBED（异步：WS/失败记录/统计）│
   │◄─ success    │                          │                       │
```

**为什么同步落库**：Lua 已把 200 并发收敛到**唯一赢家**，DB 只收到 1 条 UPDATE（≈2–5ms），异步带来的收益接近 0，却引入"接口成功但状态未落库"的窗口（取件会 40901）。v1.2 改为同步，`cr:stream:dispatch` 只承载通知类副作用与 199 条失败记录的异步批量落库。

### 3.3 派单超时三阶升级（含终止条件）

```
DispatchTimeoutTask (每 5s)
   │ ZRANGEBYSCORE cr:zset:timeout 0 now LIMIT 0 20
   ▼
dispatch_round=1 ──► 扩圈 3km + raise_fee+100 → 重推 + ZADD(+90s) → round=2
dispatch_round=2 ──► 调 AgentClient.dispatchDecide() → round=3
                     ├ 成功且 confidence≥0.6 且 金额/累计在阈值
                     │    → 执行 action（RAISE_FEE/REASSIGN）
                     │    → 写 dispatch_decision(applied=1) → ZADD(+90s)
                     └ 失败/低置信/超阈值/累计达 500
                          → 建工单 ESCALATE_CS
                          → dispatch_paused=1 + ZREM（终止自动派单）
```

### 3.4 工单初判

```
学生/骑手 → POST /ticket → ticket(PENDING)
                          → XADD cr:stream:ticket
                          ▼
              TicketStreamConsumer（Java）
                → 预计算 evidence_count / signed_at / within_window
                → HTTP POST /agent/ticket/assess（10s 超时）
                  ├ 成功 → 回写 agent_*（含 damage_level）→ 状态 REVIEWING
                  │       → WS 推运营 /topic/admin/ticket
                  └ 失败 → 状态保持 PENDING，agent_failed=1，人工直接处理
```

**注意**：Agent 初判是**异步**的，用户提交工单立即成功返回，不等待模型。

### 3.5 Agent 对话（含工具有限循环）

```
前端 → POST /api/user/agent/chat → Java 转发 /agent/chat（透传 trace_id + session 用户）
                                    ▼
                            Python：PII 脱敏 → 意图路由
                                    ▼
                    OrderAgent / ProgressAgent / ServiceAgent
                      ├ quote_price → create_order_draft → 报价卡（quote_token + draft_id）
                      └ 缺槽位 → clarify 卡
                                    ▼
                          返回 reply + slots + missing + cards
                                    ▼
用户点"确认"→ 前端带 draft_id 调 U-08（普通接口，不经 Agent）→ 支付走标准收银台
```

**关键**：Agent 只负责"问到齐"和"生成草稿"，**最终支付动作不经 Agent**。

## 4. 关键技术决策（简历上可直接讲）

| # | 决策 | 备选 | 为什么选它 |
|---|---|---|---|
| D1 | Redis Lua 抢单 + **同步** DB 确认 | 纯 DB 乐观锁 / 异步落库 | 热点行 `UPDATE ... WHERE status='WAITING'` 会让 199 个请求排队等同一把行锁（占用连接 + 事务开销），Lua 在 Redis 单线程内一次完成 5 项校验；同步落库只多 1 条 UPDATE，却消灭了"成功后回滚"的窗口 |
| D2 | 派单确定性优先，Agent 仅兜底 | Agent 全程决策 | Agent 延迟 1–3s、成本高、不稳定，不能进关键链路 |
| D3 | 缓存用"逻辑过期 + 异步互斥重建" | 纯 TTL / 只靠 Spring Cache | 热点订单详情不允许缓存集体失效；逻辑过期保证永远有值可返回 |
| D4 | 工单 Agent 初判异步化 | 同步等待模型 | 用户 200ms 返回，模型 5s 结果后到，体验与可用性都更好 |
| D5 | Agent 走工具 API 而非直连 DB | 双数据源 | 单一写入口，权限、审计、限流都可控 |
| D6 | JSON 全链路 `snake_case` | 各自习惯 | 跨 Java/Python/Vue 三语言，省掉一层命名转换 |
| D7 | 金额 `int` 分 + 六字段拆分 | BigDecimal / double | 无浮点误差；拆分后才能独立算加价上限与抽佣 |
| D8 | 状态机统一入口 | 各处 if-else 改状态 | 防跳状态；日志可回放；工单举证有据 |
| D9 | **RAG 归 Python**，Java 只提供条款原文与白名单 | Java 内嵌向量检索 | 单一 RAG 实现，避免双口径；Java 不再引入 embedding 依赖 |
| D10 | **同步落库 + Stream 只做副作用** | 全异步 | 见 D1；Stream 仍保留，用于通知、失败记录批量落库与削峰 |

## 7. 可观测设计

1. **traceId**：前端 axios 拦截器生成 `X-Trace-Id`（32 位 hex，无则后端生成），Java `TraceIdFilter` 写入 MDC 与 `LoginContext`，Python 中间件读取并注入 structlog，调用 Java 时回传 —— 三端日志用一个 ID 串起来；**trace_id 一路不可被覆盖**。
2. **业务日志**：状态变更、抢单结果、Agent 决策、退款，全部 `INFO` 且带 `order_no`。
3. **审计**：`agent_tool_log` 100% 覆盖（拦截器 finally 写）；`agent_turn_log` 每轮一条（模型、Prompt 版本、token）。
4. **告警（演示用）**：`/topic/admin/alert` 推三类：订单超时堆积（10 分钟内 > 5 单）、Agent 连续失败（3 次）、抢单异常（`cost_ms < 50` 且同一骑手 10 分钟内 > 20 次）。
