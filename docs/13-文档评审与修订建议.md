## 2. P0 · 阻断级问题（12 条，建议开工前全部修完）

> 判定标准：不改就会导致**表结构返工**、**核心时序走不通**、或**两个文档给出相反结论**。

### P0-01 状态机缺"改派 / 骑手取消"两条路径

- **证据**：`docs/02-数据库设计.md:271-280` 的迁移表没有 `ACCEPTED→WAITING`；`OrderStateMachineTest.java:39-57` 合法迁移里也没有；但 `docs/03-接口设计.md:102` 有 A-05 改派、`docs/03-接口设计.md:139` 有 `reassign_order` 工具、`docs/04-系统架构设计.md:120-127` 明确写了 `REASSIGN` 动作。
- **另一处**：`docs/01-需求规格说明书.md:161` 权限矩阵写"骑手可取消：仅本人已接未取"，但 `docs/03-接口设计.md` 骑手端 R-01~R-14 没有取消接口，状态机也只允许 ADMIN 取消 `ACCEPTED`。
- **影响**：改派在状态机上无路可走，只能绕过状态机直接 UPDATE（违反 `08` §1 硬规则 2）；骑手取消要么越权、要么矩阵与接口对不上。
- **建议**：
  1. 在 `02` §3.1 补 3 条迁移，并同步 `OrderStateMachineTest`：
     - `ACCEPTED → WAITING`（ADMIN / AGENT，改派：解绑 rider、`active_order_count-1`、`dispatch_round` 保持、写 `dispatch_decision(REASSIGN)`）
     - `EXCEPTION → WAITING`（ADMIN / AGENT，重派）
     - `DRAFT → CANCELLED`（USER / SYSTEM，未支付关闭）
  2. 骑手取消二选一：**(推荐)** 删掉 `01` §7 那一格，改为"骑手只能异常上报，由运营改派/取消"；若产品要保留，则补 `ACCEPTED → WAITING (RIDER)` + 扣信用分 + 每日次数上限。
  3. `01` §2 U-05 的"仅 WAITING 可取消"补上 DRAFT（未支付订单必须能自行关闭）。

### P0-02 "异步落库"与"抢完立刻取件"时序冲突（架构级）

- **证据**：`docs/04-系统架构设计.md:99-112` 抢单成功后 `XADD`，由消费者异步 `UPDATE`；`tests/postman/campus-run-smoke.postman_collection.json:213-247` 抢单成功后**立即**调取件接口；`docs/03-接口设计.md:82` 抢单返回 `success`。
- **影响**：消费者还没落库时 `task_order.status` 仍是 `WAITING`，取件接口按状态机返回 `40901`；演示时"抢单成功 → 点取件 → 提示状态不允许"，这是最容易被面试官看到的一类 bug。
- **更关键的技术判断**：`04` D1 说"同步写库会把 200 并发压到 MySQL"——这个论证不成立。Lua 已经把并发收敛到**唯一赢家**，DB 只会收到 **1 条 UPDATE**，200 并发下的 DB 压力与"完全同步"几乎相同；异步反而多出消息、幂等、回滚、巡检四个复杂度。
- **建议（推荐方案）**：
  1. 抢单路径改为 **同步落库**：Lua 占位成功后立即执行
     `UPDATE task_order SET rider_id=?, status='ACCEPTED', accepted_at=NOW(), version=version+1 WHERE order_no=? AND status='WAITING' AND rider_id IS NULL`，影响行数 0 才回滚 grab key。
  2. `cr:stream:dispatch` 保留，但只承载**通知类副作用**：WS 推送、`grab_record` 批量落库（199 条失败记录确实适合异步）、统计。
  3. 抢单 RT 预算改为 `Redis RTT + 1 次 UPDATE ≈ 5ms`，P99 <100ms 的指标更容易达成，答辩时这句话也更好讲。
  4. 若坚持异步：抢单出参必须改成 `status=ACCEPTING`，前端轮询/WS 收到 `ACCEPTED` 后才允许取件，并在 `01` §6 写明"最终一致窗口 ≤500ms"。

### P0-03 "确认下单"链路断裂：`draft_id` 没有入口

- **证据**：`docs/03-接口设计.md:132` `create_order_draft` 返回 `draft_id`；`docs/04-系统架构设计.md:157` 写"前端带 `draft_id` 调 `/api/user/order`"；但 `docs/03-接口设计.md:47` 的 U-08 入参只有 `quote_token`，没有 `draft_id`。
- **影响**：`04` §3.5 描述的"用户点确认 → 走普通接口"这条路，实现时无接口可调；要么前端偷偷调内部工具（违反铁律 1），要么 Agent 卡片点了没反应。
- **建议**：U-08 入参改为 `quote_token` 与 `draft_id` **二选一**（`draft_id` 优先），或新增 `POST /api/user/order/confirm`（入参 `draft_id` + `Idempotency-Key`）。同时补：
  - `cr:draft:{draft_id}` Hash/String（TTL 15min，内容 = 槽位 + quote_token + user_id），并写进 `05` key 表；
  - 草稿归属校验（`draft.user_id == 当前用户`），否则任何人拿到 draft_id 都能下单。

### P0-04 RAG 归属矛盾：`search_policy` 到底在 Java 还是 Python？

- **证据**：`docs/03-接口设计.md:131` 把 `search_policy` 定义为 **Java 内部工具**，出参带 `content` 与 `score`；`docs/06-Agent设计.md:144-155` 写的是 **Python 侧** `Chroma 检索 → 条款过滤`，`docs/04-系统架构设计.md:31-34` 架构图把 Chroma/bge 画在 Python 下面；`docs/03-接口设计.md:154` 的 `P-04 /agent/policy/reload` 又是由 Java 推 `docs[]` 给 Python 灌库。
- **影响**：如果两处都实现，会出现两个检索口径（阈值、top_k、embedding 版本不同），"条款引用准确率 100%"就无法解释；如果只实现 Java 版，Python 的 RAG 设计整章作废。
- **建议（推荐）**：**RAG 唯一归属 Python**。
  - Java 只提供 `list_policy_docs(version)`（返回 `clause_no/title/content/version/status`）供 `ingest` 与**白名单校验**使用；
  - 删除 `03` §6 的 `search_policy` 工具，改写为"Python 内部检索函数，不计入工具表"；
  - 白名单校验放在 Python（`cited ⊆ 本轮检索结果`）+ Java（写库前再校验 `clause_no` 存在于 `policy_doc` 且 `status=1`），双侧都做，才配得上"宁可不给，不可引错"。
  - 在 `04` §4 增加一条决策 D9："RAG 归 Python，Java 只做事实与白名单"，这是面试可以展开的边界。

### P0-05 费用字段口径缺失：`fee` / `urgency_fee` / 加急 / 夜间 / 系统加价 没有映射规则

- **证据**：`docs/02-数据库设计.md:121-123` 定义 `fee=基础+距离+重量`、`urgency_fee=加价（含系统加价与加急费）`（**夜间费没归属**）；`PriceCalculatorTest.java:99-136` 的 `FeeDetail.total` 却包含加急与夜间；`docs/02-数据库设计.md:313` 说"加价只能增加 `urgency_fee`，不得改 `fee`"；A-06 与 `add_urgency_fee` 的 500 分上限又按"累计加价"算。
- **影响**：`total_fee` 能对上，但三个下游全错——① 结算（抽佣基数、骑手收入）；② 加价上限（把加急 200 + 夜间 100 算进 500 上限，导致 350 分订单立刻无法加价）；③ 对账与退款（哪部分可退）。
- **建议**：把"展示/计价"与"资金入账"拆开，`FeeDetail` 增加 3 个字段并落库快照（或存 `fee_detail json`）：

  | 列 | 含义 | 是否计入 500 上限 | 抽佣 |
  |---|---|---|---|
  | `fee` | base + distance + weight | 否 | 是 |
  | `urgent_fee` | 加急 200 | 否 | 是（P-03 按实付抽佣） |
  | `night_fee` | 夜间 100 | 否 | 是 |
  | `raise_fee` | 系统/Agent 加价 | **是** | 是 |
  | `total_fee` | 以上之和 | — | — |

  同时明确：`urgency_fee = urgent_fee + night_fee + raise_fee`（保留旧列做冗余展示），累计加价只累计 `raise_fee`；`PriceCalculatorTest` 补 2 条"拆分映射"用例。

### P0-06 资金模型缺"退款 / 赔付 / 结算冲回"，部分退无法表达

- **证据**：`deploy/mysql/init/01-schema.sql:204-219` `pay_record.order_id` 是 **UNIQUE**，一单只能一条支付记录，`status` 只有 0/1/2/3；`deploy/mysql/init/02-demo-data.sql:189-194` 工单 2 对订单 1 赔付 100 分，但 `pay_record` 订单 1 仍是 `status=1`；`settlement` 已经结算 315 分，没有任何冲回；附件 P-06 丢件赔付上限 20000 分，**超过订单金额本身**。
- **影响**：① 部分赔付无法落库（只能改 pay_status=2 假装全退）；② 结算后赔付，骑手收入已发，账对不上；③ "赔付"与"退订单款"两条资金流被混成一条，工单台点"通过"到底退多少说不清。
- **建议**：
  1. 新增 `refund_record`（见 §5.2 DDL）：`order_id / ticket_id / type(ORDER_REFUND|COMPENSATION) / amount / bear_party(platform|rider) / status / idem_key`，一单可多条。
  2. `pay_status` 语义改为：`0 未支付 / 1 已支付（可含部分退）/ 2 全额退款 / 3 已关闭`；部分退款不改 `pay_status`，以 `refund_record` 为准。
  3. 结算后赔付：`bear_party=rider` 时生成 `settlement_adjustment`（负数）或在下次结算扣回；`platform` 时只减平台收入。这条规则必须写进 `附件 P-07` 与 `02` §5。
  4. `03` A-13 `resolve` 入参补 `refund_type`，并明确"赔付超过订单金额"必须走主管 + 单独补偿通道。

### P0-07 "申报价值 / 损坏等级"缺失，导致 P-02、P-05、P-06 无法执行，且评测集自相矛盾

- **证据**：
  - 附件 P-02 禁运"价值超过 500 元的贵重物品"，但 `task_order` 没有任何"申报价值"字段，下单时无法判断；
  - `RefundRuleEngine.java` 契约需要 `DamageLevel`（`RefundRuleEngineTest.java:20-25`），但 `03` P-03 出参只有 `category/liable_party/suggested_refund/cited_clauses/reply_draft/confidence`，**没有 damage_level**；
  - `ticket_samples.jsonl:19`（T-19）订单 500 分、破损，期望赔付 **20000 分**——但 P-05 上限是"订单实付 100%，且不超过 200 元"，正确值是 **500**；
  - `ticket_samples.jsonl:10`（T-10）期望丢件赔 8000 分，但样本里**没有申报价值字段**，这个数字无从得出。
- **影响**：Java 复算与模型建议必然打架；评测跑出来的"金额一致率"是假的；P-02 的贵重物品禁运在代码里无法落地。
- **建议**：
  1. `task_order` 增 `declared_value`（int，分，可空）；下单/报价时若 `>50000` 拒单（40003 + P-02），并在 `06` 槽位表加 `declared_value`。
  2. `ticket` 增 `damage_level`(LIGHT/MEDIUM/SEVERE)、`within_window`、`evidence_count`、`signed_at`；`03` P-03 入参补齐这 4 项。
  3. `06` §5.3 改口径：**模型只输出 `damage_level` 枚举 + `liable_party`，不输出百分比**；百分比与封顶由 `RefundRuleEngine` 算。
  4. 修数据：T-19 期望改 `500`（并保留 `needs_human=true`，因为涉及贵重物品违规），T-10 补 `declared_value_cent: 8000`。

### P0-08 夜间费窗口与营业时段冲突；费率"双源"

- **证据**：`docs/00-项目总览与裁剪决策.md:82` 夜间费 21:00–06:00；`docs/02-数据库设计.md:88` 与 `01-schema.sql:92-93` 服务时段 07:00–23:00；附件 P-01 说时段外"可能延迟至次日 07:00 派单"，但 `01` UC-01 的异常只有距离/禁运/报价过期，**没有时段校验**。
- **影响**：23:00–06:00 根本不能下单，夜间费实际只在 21:00–23:00 生效；"时段外是拒单还是排队"两个文档两种说法，实现时必然要临时决策。
- **建议**：
  1. 明确二选一（推荐）：**时段外直接拒单 40002**，并把夜间费窗口改为 **21:00–23:00**（与营业时段对齐）；若保留"延后派单"，则 P-01 与 `01` UC-01 都要写清"受理但排队"的状态（这需要新状态或用 `dispatch_paused` 标志，成本更高，不建议）。
  2. 费率唯一事实源定为 `policy_doc` P-03 的版本；Java `app.price.*` 只是运行时副本，**启动时校验两者一致**（版本号写进配置），不一致直接启动失败。避免"条款改了、代码没改"。

### P0-10 Redis key 与 Lua 逻辑的 5 个硬缺口

| # | 缺口 | 证据 | 后果 | 建议 |
|---|---|---|---|---|
| 1 | `cr:order:status:{order_no}` 未列入 key 表 | `05:109` 使用；`05:21-42` 22 个 key 无此项 | 实现时"凭空多一个 key"，TTL/重建/丢失策略全缺 | 补进表（Hash，无 TTL，巡检重建），并写明状态机写 DB 后同步写镜像的时序 |
| 2 | 同一骑手重复抢被当成"已被抢" | `05:106` 仅 `EXISTS` 判断；`05:201` 说"前端把'自己已抢到'识别为成功"——但 Lua 返回 0 时前端拿不到 owner | 网络重试 = 用户看到"手慢了"，实际是自己的单 | Lua 里 `GET` 后比对 `rider_id`，相同返回 `5=DUPLICATE_SUCCESS`；或 Java 侧失败后回查 owner |

### P0-11 幂等头的生成方式会让幂等失效

- **证据**：`docs/07-前端设计.md:41` "写接口调用时自动带 `Idempotency-Key: uuid()`"；`docs/03-接口设计.md:19` 五类写接口必须携带。
- **影响**：axios 拦截器每次请求都生成新 UUID，**网络超时重试 = 新 key = 重复下单**。这是幂等设计最常见的翻车点，且压测/演示时不易复现。

## 3. P1 · 设计缺口（会在联调/答辩阶段暴露，建议 W1–W3 内补）

### 3.1 Java 主流程

1. **事务边界完全没写**：哪些方法 `@Transactional`、异步/Redis/HTTP 调用为什么不能进事务、抢单落库与结算的传播行为。建议在 `08` 增一节"事务与锁边界"：`grabOrder`（Redis 后单条 UPDATE，可不开事务）、`settle`（DB 事务 + 唯一索引）、`refund`（DB 事务 + 条件更新）、`ticketReresolve`（事务 + 状态 CAS）。
2. **加价 500 上限没有并发保护**：`03` A-06 与 `add_urgency_fee` 都是"读 → 判断 → 写"，两个运营/Agent 并发会超限。建议 `UPDATE ... SET raise_fee=raise_fee+? WHERE order_no=? AND raise_fee+? <= 500` 条件更新，或 Redisson 锁 `cr:lock:raise:{no}`。巡检断言 `verify` C25 只校验单次 ≤300，缺累计校验。
3. **结算/退款/工单处理缺状态 CAS**：工单 `REVIEWING→RESOLVED` 必须带 `WHERE status='REVIEWING'`，否则两个运营同时点"通过"= 双倍赔付（`05` §9 只给 `pay_record` 做了条件更新）。
4. **改派的骑手计数与订单解绑未定义**：改派时旧骑手 `active_order_count-1`、新骑手 +1、`cr:geo` 不变、`grab` key 删除，这些都要写进 P0-01 的迁移说明里。
5. **`distance_m` 与坐标不一致**：订单 1/4 坐标直线约 **1249m** 却存 1100m，订单 6 直线约 **1330m** 却存 1200m（路网距离不可能短于直线）。需明确 `distance_m` 由谁算（建议**服务端按高德骑行路径规划算**，前端只传坐标），并按新算法重生成 6 单的 `distance_m`（金额恰好不变，但展示会矛盾）。
6. **`task_order` 无幂等键落库**：幂等只靠 Redis，Redis 重启/淘汰后重试会重复下单。建议加 `idem_key` + UNIQUE（`user_id, idem_key`），Redis 只做快路径。

### 3.2 Redis

7. **Stream 幂等键选错**：`05:129` 用 `order_no + event_type + version` 去重，但 `version` 在每次状态变更后都会变，重投的同一条消息如果被重新组装就会算出不同的键 → 重复消费。应使用 **Stream message id** 或事件自带 `event_id`（ULID）作为幂等键。
8. **`XPENDING` 重投缺实现细节**：只说"超 10 分钟未 ack 重投"，没写 `XCLAIM`（认领给存活消费者）/`XAUTOCLAIM`、消费者下线后的 pending 归属、以及重投次数上限。
9. **逻辑过期与 `cr:order:expire` 两套设计并存**：`05:22` 有独立 expire key，`05:71-77` 又说 `expire_at` 塞在 JSON 里；`09:131` 的压测还要同时 DEL 两个 key。建议只保留"JSON 内 `expire_at` + 真实 TTL 兜底"一套，删掉 `cr:order:expire`。
10. **缓存未按角色隔离**：`cr:order:detail` 同一份 JSON 服务学生/骑手/运营，`03` R-08 说"取件码仅接单人可见"、`01` U-04 说"骑手信息脱敏"。若缓存的是 VO 会串字段/泄露；若缓存的是原始实体，读时要按角色组装。建议明确：**缓存原始快照，VO 在内存组装**，并在 key 里不带角色。
11. **布隆实现选型未定**：`05:25` 写"位图/Bloom"，但 Redisson `RBloomFilter` 与手写 SETBIT 的重建、误判率、扩容完全不同。建议锁 Redisson `RBloomFilter`（依赖已在）、写明重建任务与"布隆不可用直接放行"的降级。
12. **热 key / 大 key 未治理**：订单详情是典型热 key（压测就是同一单），建议补一段：本地缓存（Caffeine）二级缓存、热 key 探测、`cr:order:detail` 单 key 限流。
13. **限流叫"令牌桶"其实是固定窗口**：`05:181-192` 的 `INCR + EXPIRE` 是固定窗口计数，边界会双倍突刺。要么改叫"固定窗口"，要么换滑动窗口 Lua / Redisson `RRateLimiter`。答辩时说"令牌桶"会被追问。
14. **抢单失败码与业务错误码两套**：Lua 返回 0/2/3/4，接口返回 `40902/40903/40301`，`09` T-10 又写"返回码 2"。建议统一：内部码只用于日志，对外一律 `code` + `fail_reason` 枚举，并在 `03` §9 补 `40906 未上线/未审核`。

### 3.3 数据与业务规则

16. **`student_no` 未加密**：附件 P-09 明确"学号采取加密存储"，但 `01-schema.sql:50` 是明文 `varchar(32)`。要么加密（与 `id_card_no` 一致），要么改条款。

### 3.4 Agent

20. **6 个意图只有 3 个 Agent**：`02:291` 枚举了 `order_progress/order_cancel/consult/chitchat`，但只有 OrderAgent/DispatchAgent/ServiceAgent；`03:67` 的 cards 里却有 `progress` 卡片。**"我的订单到哪了"没有归属**。建议加一个**规则优先的 ProgressAgent**（`list_my_orders`/`get_order` + FAQ 直答），或在 `06` 明确"这三类只走 FAQ/固定话术，不进模型"。
