# S06 · 订单查询与缓存

## 1. 目标
订单列表/详情/时间线可查，热点详情走"逻辑过期 + 互斥重建"，并解决穿透与雪崩。

## 2. 前置
S05 能下单/支付。

## 3. 产出文件

```
backend-java/src/main/java/com/campusrun/
├── controller/user/OrderQueryController.java     # U-10/U-11/U-12/U-14/U-16
├── service/{OrderQueryService,ReviewService}.java
├── cache/{OrderCacheService,CacheRebuildExecutor}.java
```

## 4. 契约

**U-10** `GET /api/user/order/page?status&page&page_size`：`status` 支持 `all/waiting/ongoing/finished/cancelled/exception`（映射见 `03` §1.2）；按 `user_id` 过滤；返回 `PageResult`。

**U-11** `GET /api/user/order/{order_no}`：
- 顺序：参数校验 → `cr:order:null` 命中返回 40401 → 布隆（S07 接入）→ `cr:order:detail` → 未命中查 DB 并回填 → 组装 VO。
- 缓存内容 = **原始快照**（订单 + 状态 + 费用 + 骑手 id），**不缓存 VO**；VO 按角色组装：学生（骑手脱敏）、骑手（取件码）、运营（全量）。
- 逻辑过期：JSON 内 `expire_at`（10min），真实 TTL 30min+rand(0,300)。
- 过期：返回旧值 + `SET NX cr:order:lock:{no}` 3s，拿锁后**异步线程池**重建；失败保留旧值。

**U-12** `GET .../timeline`：直接查 `order_status_log`，按 created_at 升序。

**U-14** `POST .../confirm`：`DELIVERED→COMPLETED(USER)`；幂等（重复确认返回 code=0）；结算在 S09 里由 `afterCommit` 触发。

**U-16** `POST .../review`：仅 `COMPLETED`；`review.order_id` 唯一；分数 1–5；写后触发信用分（S09）。

## 5. 实现要点
1. 缓存重建用独立线程池（`CacheRebuildExecutor`），不占用 Tomcat 线程。
2. 写路径（S05 的状态变更）在 `afterCommit` 删 `detail`、更新 `cr:order:status`；本步补 `OrderCacheService.evict(orderNo)`。
3. 空值缓存 TTL 2min，**建单成功后必须 DEL**（在 S05 的下单 afterCommit 里加一行）。
4. 列表不缓存；只缓存详情。
5. VO 组装禁止把 `pickup_code`/手机号放进学生 VO 的公共字段。

## 6. 禁止
- 不要在缓存里存带角色字段的 VO。
- 不要用 `@Cacheable` 一把梭（无法做逻辑过期与互斥重建）。
- 不要在读路径同步重建（阻塞请求）。
- 不要把 `cr:order:null` 的 TTL 设太长（新单会查不到）。

## 7. 验收
```bash
# T-23（确认收货→COMPLETED）
# 场景 B：50 线程压同一订单，对比缓存开关 QPS
redis-cli TTL cr:order:detail:CR20261117000001     # 应 >0
redis-cli GET cr:order:null:CR20261117009999       # 查不存在的单后应有值且 TTL≤120
# 手工把 detail JSON 的 expire_at 改到过去，再压：只应有 1 个重建线程
```
